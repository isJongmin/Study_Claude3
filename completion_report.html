Playwright MCP는 빌드된 화면에서 로그인·클릭·스크린샷으로 실제 모습을 확인하는 데 썼다(호출 횟수는 2절 표). 날씨는 백엔드가 stdio MCP(shipyard-weather)를 호출하도록 만들었다. 서브에이전트는 쓰지 않았다. ■ 결과물 검증·수정 방법 규칙은 서버가 판정하므로 pytest로 가입·승인·OTP·권한, 호선→공정→도면→결재→배포 흐름, 개정 영향, 서버 페이징·정렬을 API 수준에서 검사했다. 화면은 Playwright e2e(15개)로 주요 흐름, 360~1440px 가로 넘침 없음, 팝업 시 배경 고정, 간트 드래그, 파일 드롭을 검사했다. 변경마다 verify를 돌려 5단계가 통과한 것만 완료로 보고했다. 레이아웃은 별도 Playwright 스크립트로 임시 서버에 접속해 스크린샷과 요소 크기(도넛 크기 동일, 스크롤 높이 등)를 측정해 확인했다. ■ 막혔던 지점과 해결 - 하네스를 크게 만들었더니 실제로 돌릴 때 토큰이 많이 들었다 → 문서 크기를 줄이고(GUIDE.md 76KB → 13KB), 훅·서브에이전트·외부 스킬을 빼고, 검사는 마지막에 한 번만 하도록 바꿨다. - 전역 CSS가 한 파일에 덧붙는 구조라 뒤쪽 규칙이 앞쪽 반응형 규칙을 덮어 가로 넘침이 생김 → 반응형 규칙을 맨 뒤에 두고 grid에 minmax(0,1fr) 사용. - 간트: 막대를 놓을 때마다 이전 변경이 초기화되는 문제 → 공정별 미저장 초안(drafts)을 보관하고 상단 배너·[모두 되돌리기] 제공. - 서버 페이징 1차 구현은 전체 행을 만든 뒤 자르는 방식이라, 요청에 따라 SQL COUNT/ORDER BY/LIMIT/OFFSET으로 바꿨다(계산 열은 서브쿼리로 정렬). 결재함 대기·배포 대기도 SQL로 옮겼고, 서브쿼리 자동 상관 오류는 별칭으로 해결. - 선행 공정 선택을 칩 버튼으로 바꿨다가 기존 다중선택 select로 되돌림(요청에 따라). ■ 아쉬운 점 대시보드는 한 화면에 담지 못했다(약 1.9화면). 서버 SQL은 코드와 pytest로만 확인했고 대량 데이터 성능은 측정하지 않았다. 레이아웃은 주로 1440px에서 눈으로 확인했고 좁은 폭은 e2e 가로 넘침 검사에 의존했다. 토큰 집계는 두 단계의 세션 기록에 각각 extract_usage.py를 실행한 결과를 합친 것이다(본 구현 단계의 report_data.json은 저장되어 있지 않아 보고서 작성 시점에 1회 실행해 만들었다).
